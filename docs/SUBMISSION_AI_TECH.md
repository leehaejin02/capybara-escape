## 0. 요약 — 이 문서가 주장하는 것

이 게임은 4일 만에 만들었고, 코드·문서의 대부분은 **Claude Code의 서브에이전트 5종**이 작성했다.
그러나 이 문서가 내세우는 것은 *"AI를 많이 썼다"* 가 아니다. 그건 이제 차별점이 아니다.

**우리가 낼 것은 두 가지다.**

1. **AI에게 무엇을 금지시켰는가** — `CLAUDE.md`의 하네스 16조, 에이전트별 **도구 박탈**,
   `npm run build` 경로에 박아 둔 **기계적 경계 게이트**.
2. **분업이 실제로 무엇을 잡아냈는가** — 파이프라인이 스스로 자기 측정 기구의 고장을 발견하고
   **게임 수치 수정을 거부한 기록**, 구현자가 스펙 모순을 **반려한 기록**, 자기가 세운 논증을
   **스스로 기각한 기록**. 전부 커밋과 문서에 날짜와 함께 남아 있다.

그래서 이 문서는 **성공 사례가 아니라 분업이 실제로 무엇을 잡아냈는지**를 싣는다(§5).
결과물 한 줄보다, 그 결과가 어떤 구조에서 나왔는지가 이 파이프라인의 물증이라고 판단했다.

## 2. 구조 (1) — 에이전트 5종과 **도구 제한**

짧은 일정에서 **AI 에이전트 5종에게 역할을 나눴고**, 「팀원 롤 기술서」가 팀에게 묻는 것
(*담당 역할 / 실제로 구현한 영역 / 협업·분업 방식*)을 **그 에이전트들에 대입해** 여기 적는다.

정의 파일은 저장소의 `.claude/agents/*.md` 5개다. 각 파일의 프론트매터에 **그 에이전트가 쓸 수 있는
도구 목록**이 들어 있고, **이 목록이 이 설계의 핵심이다.**

| 에이전트 | 담당 | 소유(쓰기 가능) 파일 | 부여한 도구 | model |
|---|---|---|---|---|
| `director` | 인텐트 복원 → 메타 프롬프트 → 라우팅 | 없음 | Read, Glob, Grep, **Write** | opus |
| `gd` | 무엇을 만들까 / 규칙·수치 | `docs/**`, `src/config/balance.ts` | Read, Glob, Grep, Write, Edit | opus |
| `tech` | 어떻게 만들까 / 코드 | `src/**` (`balance.ts` 제외) | Read, Glob, Grep, Write, Edit, **Bash·PowerShell** | sonnet |
| `playtest` | 수치가 맞는가 (헤드리스 시뮬) | **없음 (읽기 전용)** | Read, Glob, Grep, **Bash·PowerShell** — Write·Edit **없음** | sonnet |
| `verify` | 완료 기준을 만족하는가 | **없음 (읽기 전용)** | Read, Glob, Grep, **Bash·PowerShell** — Write·Edit **없음** | sonnet |

### 왜 도구를 잘랐는가

- **`playtest`·`verify`에서 Write·Edit을 뺀 것이 이 설계에서 가장 중요한 결정이다.**
  검증자가 코드를 고칠 수 있으면, 미달을 발견했을 때 **보고하는 대신 고쳐서 통과시키는 것**이 항상 더 싸다.
  그 순간 검증은 자기 채점이 된다. 두 정의 파일에 그 이유를 못박아 뒀다.

  > `verify.md` — *"너는 검증 담당이다. **고치지 마라 — 찾아라.** Write·Edit이 없는 건 실수가 아니라
  > 설계다. 조사와 수정을 같은 손이 하면 검증이 아니라 자기 채점이 된다."*
  >
  > `playtest.md` — *"너는 **코드를 고칠 수 없다.** 측정하고 반려하는 게 임무다.
  > **그 경계가 네 신뢰성의 근거다.**"*

- **`director`에게 Edit이 없다.** 총괄은 기존 파일을 고칠 수 없다 — 라우팅 문서만 새로 쓴다.
  *"코드를 쓰지 마라. 게임 밸런스를 직접 정하지 마라."*
- **`gd`에게 Bash가 없다.** 디자이너는 **자기 수치를 스스로 실행해 검증할 수 없다.**
  불편해 보이지만 의도한 것이다 — 검증은 반드시 `playtest`(다른 컨텍스트, 다른 모델)를 거친다.
- **`tech`에게 `docs/GDD.md`·`balance.ts` 쓰기를 금지**했다. 구현자가 밸런스를 만지기 시작하면
  "수치가 왜 이 값인가"의 원본이 두 곳이 되고, `playtest` ↔ `gd` 왕복의 주체가 사라진다.
- 모델도 역할에 맞춰 나눴다. **판단·설계는 opus, 실행·측정은 sonnet.**

### 기본 흐름

```
director → gd → [사용자 승인] → tech → playtest → verify
```

`CLAUDE.md`는 이 흐름에 두 가지를 덧붙인다.

> *"단계를 건너뛰는 건 허용된다. 단 **왜 건너뛰는지 반드시 밝힌다.** 조용한 생략은 금지다."*

그리고 **발화 → 절차 연결표**를 둬서, 사람이 절차를 기억하지 않아도 되게 했다.
*"다 됐나?"* 라는 말이 들어오면 `verify`를 부르고, **그 전에는 "완료"라고 말하지 않는다.**
*"밸런스 어때?"* 는 `playtest` 호출 후 **그 숫자로만** 답한다.

## 3. 구조 (2) — 아키텍처 하네스: 코드가 강제하는 경계

### 3.1 `src/sim/`은 Phaser를 import할 수 없다

이 프로젝트의 게임 규칙은 전부 `src/sim/` 아래에 있고, **브라우저 없이 Node에서 돈다.**

```
src/sim/   — 규칙 (map / raycast / vision / movement / goblin / mission / bot / world)
src/scenes/— 렌더 (Phaser). sim의 상태를 그리기만 한다
src/config/balance.ts — 모든 밸런스 수치의 유일한 원본. import 0개
```

**이 경계가 없으면 `playtest` 에이전트가 성립하지 않는다.** 규칙이 Phaser에 묶이는 순간
헤드리스 시뮬(`npm run sim`)이 불가능해지고, 밸런스는 "사람이 몇 판 해 보고 감으로" 정하는 것으로 돌아간다.
그 순간 이 프로젝트의 차별점이 통째로 사라진다. 그래서 하네스 1조가 이렇게 쓰여 있다.

> *"**`src/sim/` 아래에서 Phaser를 import하지 않는다.** (…) 이 경계가 무너지면 `playtest` 에이전트가
> 성립하지 않고, 그건 이 프로젝트의 핵심 차별점을 잃는 것이다."*

### 3.2 `scripts/check-boundary.mjs` — 유일하게 실제로 작동하는 게이트

관습으로는 반드시 깨진다고 보고, **무의존 정적 스캐너**를 직접 만들어 `npm run sim`과 `npm run build`
**양쪽 크리티컬 패스**에 걸었다. 빌드하려면 반드시 통과해야 한다.

```json
"check": "node scripts/check-boundary.mjs",
"build": "npm run check && vite build",
"sim":   "node scripts/check-boundary.mjs && tsc -p tsconfig.sim.json && node dist-sim/tools/sim-cli.js"
```

- 6종 import 형태(기본 / `import type` / side-effect / re-export / 동적 `import()` / `require()`)를
  **문자 단위 상태 기계**로 스캔한다. 줄 단위 정규식이 아니라서 여러 줄 import도, 주석·문자열 안의
  가짜 import도 정확히 구분한다.
- **스캔한 파일이 0개면 스스로 실패한다.** 코드 주석 원문:
  *"경로 오타 또는 리팩터링으로 폴더가 옮겨져 검사기가 아무것도 읽지 못했을 가능성이 높다.
  이 상태로 통과시키는 것이 가장 위험한 실패 모드이므로 무조건 실패시킨다."*
- **알려진 한계를 고치지 않고 명시했다** — 템플릿 리터럴 동적 import, 변수로 만든 지정자.
  정적 스캐너의 구조적 한계라 "막힌다"고 쓰지 않았다.

### 3.3 그리고 이 장치에 대해 우리가 처음 쓴 설명은 **틀렸다** (D1 정정)

착수 시 결정문 D1은 세 장치가 **각각 독립적으로** 경계를 막는 "3중 방어"라고 적었다.
`tech`가 구현 중 실측으로 그게 사실이 아님을 밝혔고, 사용자가 독립 재현했고,
`verify`가 문서에 남아 있던 과장 표현 2곳을 잡아냈다.

| 장치 | 기대 | 실측 결과 |
|---|---|---|
| `scripts/check-boundary.mjs` | 1차 | **유일한 실질 게이트** |
| `tsconfig.sim.json` | 2차 | **막지 못한다.** sim에 `import Phaser from 'phaser'`를 넣어도 `tsc`가 exit 0. TypeScript에 "이 디렉터리에서 이 패키지 금지" 옵션이 없다 (`moduleResolution: "Classic"`은 TS7에서 제거, `paths` 리맵은 실패 시 node 해석으로 폴백) |
| 런타임 크래시 | 3차 | **조건부.** 미사용 import는 tsc가 지워버려 발동조차 안 한다. `import type`은 영원히 못 잡는다 |

> 검사기 파일 상단 주석에 이 사실을 그대로 적어 뒀다 — *"즉 **이 스크립트가 죽으면 아무도 경계를
> 지키지 않는다.**"*

**이 정정을 장치 자랑보다 앞에 두는 이유**: "3중이라 안전하다"는 문구를 믿으면, 실제로는 파일 하나에
매달린 경계를 무방비로 방치하게 된다. 정정 후 `verify`가 **import 형태 13종**으로 교차 검증했고
**오탐·미탐 0건**이었다.

## 4. AI 대상 주요 프롬프트 및 지시 사항

지시의 원본은 저장소 루트의 **`CLAUDE.md`** 하나다. 모든 세션·모든 에이전트가 이 파일을 먼저 읽는다.
핵심은 **"하지 마라"의 목록**이고, 각 조항은 **실제로 일어났거나 일어날 뻔한 실패**에서 역산해 만들었다.

| # | 원문 | 막으려는 실패 |
|---|---|---|
| 1 | *"`src/sim/` 아래에서 Phaser를 import하지 않는다."* | 편의를 위한 한 줄이 `playtest` 에이전트를 통째로 무효화하는 것 |

| 8 | *"새 npm 의존성은 **승인 없이 추가하지 않는다.**"* | 심사자 재현성 파괴 + 라이선스 추적 불가 |
| 9 | *"커밋을 마지막에 몰아서 하지 않는다."* | "커밋 기록 유지"가 제출 요건이고, **단계별 커밋이 곧 이 문서의 물증**이다 |
| 10 | *"외부 에셋·오픈소스를 가져오는 순간 `docs/ASSET_CREDITS.md`에 출처와 라이선스를 적는다. 나중에 추적하지 않는다."* | 무단 도용 = **선발 취소**. 사후 추적은 반드시 빠진다 |
| 11 | *"유료 라이선스가 필요한 것을 쓰지 않는다."* | 심사자가 추가 비용 없이 실행해야 한다 |
| 12 | *"플레이 영상은 실제 플레이 화면만 쓴다. AI 합성·조작·타인 영상 도용은 규정 위반이다."* | 생성 AI를 쓰는 프로젝트에서 가장 위험한 유혹 |
| 13 | *"마감 당일에 처음 배포하지 않는다 — 배포는 하루 앞서 끝낸다."* | §5의 배포 사고가 정확히 이 조항이 막은 것이다 |
| 14 | *"확인 못 한 것을 통과로 보고하지 않는다. 실행 대신 정적 분석·계산으로 대체했으면 '실측 아님'을 반드시 명시한다."* | LLM의 기본 실패 모드. **모든 결정문에 「실측이 아닌 것」 절을 강제**하는 것으로 집행했다 |
| 15 | *"작업 중 이상한 걸 발견하면 무조건 말한다. (…) 조용히 우회하지 않는다."* | **§5의 결함 발견 경로 그 자체다.** 이 조항이 없으면 아래 사례 전부가 침묵으로 지나간다 |
| 16 | *"밸런스는 감으로 확정하지 않는다. **`playtest` 측정 없이 '밸런스 맞췄다'고 쓰지 않는다.**"* | §5-A(D8)가 이 조항의 극단적 적용이다 |

### 4.2 조항이 실제로 집행된 방식

- **하네스 14 → 문서 서식으로 강제.** `docs/DECISIONS.md`의 D7~D13은 **전부 「실측이 아닌 것」 절로
  끝난다.** 예: D13-f — *"`gd`는 이번 세션에 코드를 한 줄도 읽지 않고 실행하지 않았다."*
  WORKLOG의 모든 세션에도 「확인 못 한 것」 절이 있다. **자백란을 서식에 박아 두면 채우게 된다.**
- **하네스 7 → D12-c.** 맵을 1개에서 3개로 늘릴 때, 같은 결정문에 **버린 것 5개**를 같이 적었다
  (SHOULD 목록 전부 WON'T로 / 아트 재작업 0회 / 밸런스 조정 0회 / 시각 판정 1회 / 스펙 1건 폐기).
  GDD 10장 SHOULD 목록은 그때 **비워졌다.**
- **하네스 16 → D8.** §5-A.
- **에이전트 정의 파일에도 같은 언어를 넣었다.**
  `gd.md` — *"**「안 만들 것」을 정하는 게 디자이너의 주 업무다.** 기능을 늘려 재미를 만들려 하지 마라."*
  `tech.md` — *"스펙에 **없는 결정이 필요해지면 임의로 정하지 말고 멈춰서 보고**한다.
  이게 가장 흔한 사고 지점이다."*
  `playtest.md` — *"시뮬이 통과해도 그건 **「안 깨졌다」이지 「재미있다」가 아니다.**"*

## 5. 본론 — 파이프라인이 스스로 잡아낸 결함 7건

여기부터가 이 문서의 실질이다. 아래는 전부 **커밋과 문서에 남아 있는 실제 기록**이며,
"AI가 잘 만들었다"가 아니라 **"분업이 무엇을 잡았는가"** 의 사례다.

### A. `playtest`가 측정 기구의 고장을 발견했고, `gd`가 게임 수정을 **거부**했다 (D8)

밸런스 라운드 2에서 클리어율이 7.0% → 12.9%로 올랐지만 목표(35~55%)에 한참 못 미쳤다.
`gd`가 미리 짜 둔 분기표는 이 갈래에서 **봇의 실효 이동속도를 먼저 재라**고 지시했다. 결과:

| 측정 | 값 |
|---|---|
| 이론상 이격 속도 (`PLAYER 90 − GOBLIN CHASE 75`) | **15 px/s** |
| **실측 이격 속도** (추격 중 고블린 300px 이내 전 틱) | **2.2 px/s — 이론값의 15%** |
| 순간 속도 실현율 (벽 충돌 손실) | 90.8% → **9% 손실로는 설명되지 않는다** |

즉 **봇은 이 게임의 핵심 동사인 "도망친다"를 실행하지 못하고 있었다.**
그렇다면 12.9%는 게임의 클리어율이 아니라 **사람 클리어율의 하한**이고, 진짜 값이 목표 대역의
위인지 아래인지조차 모른다. `gd`의 판정은 **밸런스 축 전체 동결**이었다 — `balance.ts` 게임 수치 변경 0건.

> `docs/GDD.md` 11장에 남긴 문장 —
> *"고장 난 자로 잰 값에 맞춰 게임 수치를 깎는 것은 이 조항을 만족시키는 게 아니라 **위조하는 것**이므로
> 하지 않는다."*
>
> `docs/RULES.md` §7.0에 추가한 대칭 규칙 —
> *"**봇이 고장 난 것을 보상하려고 게임 수치를 깎아도 측정은 무의미해진다.** 이쪽이 더 위험하다 —
> 앞쪽은 봇에 흔적이 남지만, 이쪽은 **게임 수치에 영구히 새겨지고 나중에 어느 값이 봇 결함의
> 보상분이었는지 구분할 수 없게 된다.**"*

**목표 지표(`TARGET`)도 GDD 11장 7번도 완화하지 않았다.**

같은 결정문에서 `gd`는 **자기가 이전 라운드에 쓴 추정 하나를 스스로 폐기**했다. "CHASE 축이 VISION 대비
2배 효율"이라는 D7-b의 주장은 두 점으로 그은 직선의 외삽이었고, 세 번째 점(0.408 → **0.136** %p/상대1%)이
그것을 깼다. → 원칙 추가: **축 효율은 측정된 구간 안에서만 인용한다.**

### B. `gd`가 **고치기 전에 반증할 기회**를 설계했고, 자기 가설이 기각됐다 (세션 4)

A의 후속으로 `bot.ts` 수정 스펙(`SPEC_BOT_FLEE_FIX.md`)을 썼다. 원인 가설은 *"도주 방향을 위협들의
단위벡터 합으로 구하는데, 고블린이 둘 이상이면 합이 상쇄돼 방향이 진동한다"* 였다.

**코드를 고치기 전에 0단계로 사전 측정을 넣고, 판정 기준을 측정 전에 고정했다**
(반전율 ≥10% 착수 / 5~10% 회색 / <5% 기각).

| 항목 | 값 |
|---|---|
| FLEE 틱 총합 | 1,843,099 |
| **방향 반전율** (직전 FLEE 틱과 90° 초과) | **3.93% → 기각** |
| 6시드 범위 | 3.67 ~ 4.17% (전부 5% 미만) |
| `gd`가 원인으로 지목한 폴백 경로(B2) 발동 | **184만 틱 중 0회** |

→ **`bot.ts`를 한 줄도 건드리지 않았고, 스펙 전체를 폐기했다.**
이 게이트가 없었으면 멀쩡한 코드를 뜯어고치고 **나서야** 원인이 아님을 알았을 것이다.

### C. `tech`가 스펙의 **내부 모순**을 반려했다 (D10)

`SPEC_ZONES.md` §3.5의 W2는 *"12개 벽 프레임 전부의 앞면에 밝기 상한 117"* 을 요구하는데,
같은 문서 §3.2는 *"variant 1·3은 프레임 전체가 윗면"* 이라고 정의한다. 윗면 색은 상한을 넘는다.
→ **동시 만족이 원리적으로 불가능하다.**

`tech`는 조용히 한쪽을 무시하지 않고 **멈춰서 반려했다**(하네스 15).
`gd` 판정: 문턱값 117은 **한 개도 바꾸지 않고**, 적용 대상을 "앞면이 있는 6프레임"으로 명문화했다.
완화가 아니라 **범위 기술의 누락**이었다.

> 이때 드러난 것: 같은 문서 §6의 **기계 검사 항목 A15는 처음부터 "앞면 있는 변형(0·2)"으로 옳게
> 적혀 있었다.** 범위를 **알고 있었는데 사람이 읽는 문장에만 안 적었다.**
> 사람용 문장과 기계용 문장이 갈라져 있었던 것이다.

같은 계열의 결함이 **세 번** 반복됐고(D1 "3중 방어" / 터널링 안전 논증의 적용 범위 / C1-W 적용 대상),
셋 다 **쓰는 쪽이 아니라 읽는 쪽**이 발견했다. → 프로세스 규칙으로 승격:
**`gd`는 조건과 적용 대상을 같은 줄에 쓴다. "전부"라고 쓰고 싶으면 그 "전부"가 몇 개인지 센다.**

### D. `tech`가 자기 권한으로 통과시킬 수 있었는데 **판단을 반려**했다 (D11)

숲 벽과 수풀의 판별 조건 C12를 PNG로 처음 실측했더니 **26.7 (문턱 35, 실패)** 이 나왔다.
그런데 스펙이 측정 영역(`wall̄`)을 정의하지 않아 두 해석이 가능했고, **다른 해석으로는 49.0으로 통과**였다.

`tech`는 통과하는 해석을 골라 넘기지도, 색을 몇 픽셀 고쳐 통과시키지도 않고 **두 값을 모두 보고했다.**
`gd` 판정: **프레임 전체가 맞다**(윗면이 면적의 53%이고, C12가 묻는 것은 "이 덩어리를 지나갈 수
있는가"이므로 덩어리 대 덩어리 비교여야 한다). → **반려된 것은 `tech`가 아니라 스펙의 공백이었다.**

처방도 색 조정이 아니라 **재질 교체**(초록 잎 벽 → 이끼 낀 돌담)였다. 원인이 색이 아니라
*타일은 32px 주기로 반복되므로 반복되는 유기물은 격자로 읽히고, 격자를 흐리려 둥글게 만들면 덤불이 된다*
는 구조적 문제였기 때문이다. **C12 26.7 → 58.4 실측.**

그리고 진짜 성과는 수치가 아니라 규칙 한 줄이었다 — **"숲에서 초록은 전부 통과 가능하다"
(숲 벽에 초록 0픽셀).** 연속량(평균 대비 35 이상)은 언제나 아슬아슬하지만, **0/1 판정은 `verify`가
기계적으로 검사할 수 있고 플레이어가 한 판 안에 학습한다.**

### E. 에이전트 분업이 **잡을 수 없는** 결함 — 사용자만이 잡았다 (D12)

사용자의 원래 지시는 *"맵이 3개인데 랜덤하게 나온다"* 였다.
`gd`는 이것을 **한 맵의 세로 3구역**으로 읽었고, 코디네이터가 그대로 승인했다.
**사용자가 직접 플레이해 보고서야 잡혔다.**

**경보는 우리가 직접 울렸다.** `SPEC_ZONES.md` §5.1에 `gd`가 써 둔 문장이 있다.

> *"발주 지시와 남북을 뒤집었다 — 그 이유"*

지시와 구현이 안 맞는다는 것을 **알고 있었고**, 그 불일치를 혼자 해소한 뒤 **각주로 남겼다.**
그런데 진짜 불일치는 방위가 아니라 **단위**였다 — 지시의 "3"은 맵 3개였고 우리는 구역 3개로 읽었다.
**작은 불일치(방위)를 성공적으로 해소한 것이, 큰 불일치(단위)를 덮었다.**

**이 결함은 `tech`도 `verify`도 잡을 수 없다. 코드는 스펙대로 완벽히 동작하고 있었기 때문이다.**

> `docs/DECISIONS.md` D12-b —
> *"**에이전트 분업이 못 잡는 결함의 유일한 종류가 이것이다 — 발주 해석의 오류.
> 그래서 사용자를 루프에서 빼면 안 된다.**"*

→ 규칙: **`gd`가 발주 문장을 다른 뜻으로 바꿔 읽으면, 스펙을 쓰기 전에 한 줄 질문으로 되돌린다.
문서에 "지시와 다르게 했다"고 쓰고 싶어지는 순간이 바로 그 지점이다.**
판별도 어렵지 않다 — **자기 문서에 경고 표시를 다는 순간이 신호다.**
장치가 없었던 게 아니라 **장치를 켜 놓고 그냥 지나갔다.**

(손실은 작았다. 타일 3세트가 이미 구워져 있어 **아트 재작업 0건**이었고, 행 단위 구역 판정이
맵 단위 테마로 바뀌면서 **렌더 코드가 오히려 단순해졌다.**)

### F. 게이트 **밖의** 관측치가 게이트의 정당성을 무너뜨렸다 (D13)

맵이 3개가 된 뒤 맵별 균형 게이트를 돌렸다(맵당 1200회).

| 맵 | clearRate | avgMissions | **stuckRuns** |
|---|---|---|---|
| 0 village | 13.6% | 2.83 | 0.8% |
| 1 forest | 4.0% | 1.33 | **27.6%** |
| 2 cave | 1.7% | 2.36 | 0.0% |

**PG2 위반**: 13.6 / 1.7 = **8.13** (문턱 2.5). 스펙의 처방은 *"중앙값에서 가장 먼 맵을 뺀다"* 인데,
실측 {13.6, 4.0, 1.7}에서 중앙값은 4.0이고 **가장 잘 나온 village가 제거 대상**이 된다.
`tech`가 이 모순을 잡고 **임의 판단을 거부해 반려했다.**

그리고 `gd`는 **자기가 세운 논증을 스스로 기각했다.** D12-f에 이렇게 써 뒀었다.

> *"비율은 **같은 고장 난 자로 세 맵을 잰 것**이라 자의 편향이 상쇄된다."*

**틀렸다.** 편향이 비율에서 상쇄되려면 봇의 결함이 세 맵에 **같은 배율로** 작용해야 한다.
`stuckRuns` **27.6% vs 0.8% vs 0.0%** 가 그렇지 않다는 직접 증거다 — 숲에서만 봇이 4판 중 1판꼴로
진행 불능에 빠진다. **비율도 오염돼 있었다.**

> D13-c — *"「비율을 쓰면 공통 편향이 사라진다」는 명제는 **참인 정리**다. 내가 안 쓴 것은 그 정리의
> **전제**다 — 편향이 공통일 것."*
>
> 그리고 이 반례를 들고 온 `stuckRuns`는 **게이트 항목이 아니었다.**
> → 관찰: **측정은 문턱 이외의 것도 같이 찍어 둬야 한다.**

**처방은 유예했지만 기록은 실패로 남겼다.** 문턱 2.5는 한 자리도 바꾸지 않았고(`balance.ts` 0바이트 수정),
대체 판정으로 **사람 직접 플레이 게이트 HG1~HG4**를 만들되 **기준을 플레이 전에 고정**했다
(도달 불가능한 미션 지점 / 탈출 불가 / 진행 불능 / 완료 미션 2개 이하 — 전부 0/1 판정).
연속량이 아슬아슬하면 **이산 판정으로 바꾼다**는 D11의 규칙과 같은 처방이다.

### G. "UI가 허접하다"의 원인은 디자인이 아니라 **고장**이었다 (세션 6)

사용자가 레퍼런스 앱을 제시하며 UI 전면 개편을 요구했다.
**그 방향으로 바로 가지 않고 화면을 먼저 측정했다.**

```
devicePixelRatio = 1.1  /  backingStore 960×640  /  CSS 960×640
→ 게임 1픽셀 = 물리 1.1픽셀 (비정수)
```

`pixelArt: true`는 NEAREST 샘플링이라 **비정수 배율에서 픽셀이 불규칙하게 중복·소실된다.**
한글은 14~18px에서 획이 1px이라 **그 획이 통째로 날아가고 있었다.**

| 화면 | 의도한 글자 | 실제로 보이던 것 |
|---|---|---|
| 커스터마이즈 | `몸 / 옷 / 모자` | `늠 / 읏 / 므자` |
| 커스터마이즈 하단 | `↑↓ 항목 선택 · ←→ 변경` | `펑쪽 세택 · 쳔컬` |
| 인게임 HUD | `남은 시간 3:00` | `님은 ㅅ가 3:00` |

**디자인 문제가 아니라 렌더 고장이었다.** 수리는 백킹스토어를 그대로 두고 CSS 표시 크기만
`960·N/dpr`로 잡아 **물리픽셀/게임픽셀 = 정수 N**을 보장하는 것이다. 실측 1.1 → 1.0000.
씬 4개·미니게임 3종 **재배치 0건**, 아트 재작업 **0건** — D12-c가 이미 버려 둔 항목을 되살리지 않고 해결했다.

> **그리고 이때 더 나쁜 것을 발견했다.** `docs/GDD.md` 251행과 `.claude/agents/tech.md`는 둘 다
> **"정수 스케일만"** 을 규칙으로 적어 뒀는데, **`src/main.ts`에는 `scale` 설정 자체가 없었다.**
> 규칙은 세 세션 내내 문서에만 있었고, **dpr이 1.0인 머신에서만 우연히 지켜지고 있었다.**
> D1과 같은 계열이다 — **장치가 있다고 적혀 있는데 없었다.**
> (지금은 `main.ts`의 `applyIntegerPixelScale()`이 코드로 강제한다.)

## 6. 관통하는 관찰 — 무엇이 실효였는가

위 7건 중 A·B는 측정하는 쪽이, C·D·F는 구현하는 쪽이, G는 사람이 잡았다. 공통 구조가 있다.

> **결함은 거의 전부 "쓰는 쪽의 암묵 전제를 읽는 쪽이 실행으로 강제 노출시켜서" 잡혔다.**

- 쓰는 사람은 적용 범위·전제·방향을 **머릿속에 갖고 있어서 안 적는다.**
- 읽는 사람은 그게 없다는 것을 **실행해 봐야 안다.**

그래서 실효였던 것은 **역할을 나눈 것 자체가 아니라, 읽는 쪽에 실행 권한(Bash)과 반려 권한을 준 것**이다.
`tech`·`playtest`·`verify`는 전부 Bash를 갖고 있고, `playtest`·`verify`는 **Write를 갖고 있지 않다.**
고칠 수 없으니 **말하는 것 말고 할 수 있는 일이 없다.** 하네스 15가 그 말할 통로를 열어 준 장치다.

**대조군을 돌린 적은 없다** — 단일 에이전트로 같은 4일을 다시 살아 볼 수는 없었다. 다만 위 7건 중 **C·D·F는 「쓴 쪽과 읽는 쪽이 달랐기 때문에」 잡혔다고 본다**(추정이다). 같은 컨텍스트가 쓰고 같은 컨텍스트가 읽으면
암묵 전제가 노출되지 않는다.

**그리고 E는 그 구조로도 못 잡는다.** 코드가 스펙대로 완벽히 동작하는 결함 —
**발주 해석의 오류**는 실행으로 절대 드러나지 않는다. **그래서 사람을 루프에서 빼면 안 된다.**

32×32 규격에 맞춰 새로 설계했다. 레퍼런스 파일은 **커밋하지 않았다.**
(아이디어·스타일은 저작권 보호 대상이 아니지만 표현은 보호 대상이므로, 이 구분을 지킨 사실을 기록한다.)

### 7.3 오픈소스 의존성 — **실제 설치본에서 확인한 값**

`node_modules/<pkg>/package.json`의 `license` 필드를 직접 읽어 대조했다.

| 패키지 | 설치 버전 | 라이선스 | 용도 | 빌드 산출물 포함 |
|---|---|---|---|---|
| `phaser` | 3.90.0 | **MIT** | 게임 엔진 | 포함 |
| `vite` | 8.2.0 | **MIT** | 번들러 | 빌드 전용 |
| `typescript` | 7.0.2 | **Apache-2.0** | 컴파일러 | 빌드 전용 |
| `@types/node` | 26.1.2 | **MIT** | 타입 정의 (런타임 코드 없음) | 빌드 전용 |

**직접 의존성은 이 4개가 전부다.** `@types/node`는 하네스 8("새 npm 의존성은 승인 없이 추가하지
않는다")의 **유일한 승인 예외**이며, 결정문 D2에 이유와 함께 남아 있다
(*"`src/tools/sim-cli.ts`가 `process.argv`를 읽어야 한다. 타입 전용이라 번들에 런타임 코드가
들어가지 않는다. **eslint / prettier / vitest / tsx / ts-node는 요청하지 않으며, 요청이 와도 거절한다**"*).

CI에서 쓰는 GitHub 공식 액션(`actions/checkout`, `actions/setup-node`)은 MIT이며 빌드 산출물에
포함되지 않는다. **유료 라이선스가 필요한 것은 하나도 쓰지 않았다**(하네스 11) —
심사자는 `npm ci && npm run build`만으로 전 과정을 재현할 수 있다.

### 7.4 에셋 제작에만 쓴 외부 도구 (게임에 포함되지 않음)

| 도구 | 라이선스 | 실제 사용 방식 |
|---|---|---|
| [sprite-gen](https://github.com/aldegad/sprite-gen) (aldegad) | **Apache-2.0** | **교차검증(QA)에만 사용.** 저장소에 코드·산출물 미포함 |

당초 계획은 카피바라 4색 컬러웨이를 이 도구의 `recolor`로 굽는 것이었으나,
**(1) 새 의존성 0개 원칙, (2) 심사자가 외부 파이썬 도구 없이 재현할 수 있어야 한다**는 이유로
리컬러를 순수 JS로 직접 구현했다. sprite-gen은 대신 **우리 출력과 대조하는 데 썼고,
디코딩된 raw RGBA가 바이트 단위로 동일**했다 — 우리 구현이 검증된 도구와 같은 결과를 낸다는 독립 근거다.

> **저장소의 어떤 산출물도 sprite-gen이 만든 것이 아니다.** 그럼에도 실제로 실행했으므로 출처를 남긴다.
> 검토했다가 채택하지 않은 도구(perfectpixel-studio, MIT)도 미채택 사유와 함께 `ASSET_CREDITS.md`에 있다.

### 8.3 명시적 생략의 기록

하네스는 단계 생략을 허용하되 **조용한 생략을 금지**한다. 실제로 생략할 때마다 이유를 남겼다.

*"고블린·미션·맵이 없는 상태에서 시뮬을 돌리면 **의미 없는 숫자**가 나온다. 그걸 근거로 남기는 것은
하네스 16을 형식적으로만 만족시키는 가짜 근거이고, 곧 하네스 14 위반이다."*
→ 대신 시뮬 출력에 `!! STUB` 배너와 JSON `"stub": true`를 넣고, `--assert`가 stub인 동안
**무조건 실패(exit 2)** 하게 만들었다. **시스템이 스스로 "아직 밸런스 자료가 아니다"라고 말하게 한 것이다.**
