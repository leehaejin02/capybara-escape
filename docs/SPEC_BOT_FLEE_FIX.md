## 1. 무엇이 잘못됐나

`playtest` 라운드 2 계측 (6시드 × 200회, `CHASE_SPEED` 75):

| 측정 | 값 |
|---|---|
| 이론 이격 속도 (`BASE 90 − CHASE 75`) | 15 px/s |
| **실측 이격 속도** (CHASE 중 고블린 300px 이내 전 틱) | **2.2 px/s (이론의 15%)** |
| 순간 속도 실현율 (벽 충돌 손실) | 90.8% |

**벽 손실 9%로는 85%p의 격차를 설명할 수 없다.** 속력은 나오는데 **방향이 틀리다**는 뜻이다.
봇이 이 게임의 핵심 동사인 "도망친다"를 실행하지 못하고 있고, 그 상태로 잰 클리어율(12.9%)은
게임이 아니라 봇을 측정한 값이다. 그래서 `gd`는 밸런스 조정을 D8에서 동결했다.

### 유력 원인 — `computeFleeDir`의 단위벡터 합 (`bot.ts` 164~187행, `RULES.md` §7.5)

```ts
sum += d / |d|            // 거리 무관 동등 가중
if (|sum| < 1e-6) sum = -bot.facing
```

두 개의 결함이 겹쳐 있다.

**결함 B1 — 상쇄 근처에서 방향이 노이즈로 결정된다.**
가중치가 거리와 무관하므로, 위협 2마리가 서로 반대편에 있으면 `|sum| → 0`이 된다.
문제는 `|sum|`이 정확히 0일 때가 아니라 **0에 가까울 때**다. `normalize(sum)`이 서브픽셀 크기의
잔차를 **길이 1의 완전한 방향 벡터로 증폭**한다. 고블린 위치는 매 틱 미세하게 움직이므로
그 잔차의 부호가 계속 뒤집힌다 → 도주 방향이 틱마다 크게 흔들린다.
`< 1e-6` 가드는 **정확한 상쇄만** 잡고, 실제로 위험한 구간(`|sum|` ≈ 0.01~0.3)은 그대로 통과시킨다.

**결함 B2 — 폴백이 위협 쪽을 가리킨다.**
상쇄 시 `sum = -bot.facing`인데, FLEE 중의 `bot.facing`은 **직전 도주 방향**이다.
따라서 `-facing`은 "방금 도망쳐 온 쪽" = **위협 쪽**이다. 게다가 그 틱에 그리로 움직이면
다음 틱의 `facing`이 다시 뒤집혀 **180° 진동의 자기유지 루프**가 된다.

> 이 지목은 `playtest`의 코드 분석 + 정황 수치이고 **아직 재현 실험으로 확정되지 않았다**(하네스 14).
> 그래서 §3의 **0단계**에 반증 가능한 사전 측정을 넣었다. **0단계 없이 코드를 고치지 마라.**

## 2. 규칙 — 어떻게 고치나

### 0단계 (선행 · `playtest` · tech 시간 0)

`bot.ts`를 **고치기 전에** 아래 지표를 먼저 잰다. 가설이 틀렸으면 여기서 끝낸다.

> **FLEE 방향 반전율** := FLEE 모드인 틱 중, **직전 FLEE 틱의 최종 이동 방향**(jitter 적용 후,
> `SimInput.moveX/moveY`)과의 각도차가 **90°를 넘는** 틱의 비율.
> FLEE가 끊겼다가 다시 시작된 첫 틱은 분모·분자에서 제외한다.

조건: 6시드 × 200회, `balance.ts` 무변경.

### B1 — 거리 가중 (`computeFleeDir`)

단위벡터 동등 가중을 **가까울수록 큰 선형 가중**으로 바꾼다. 가장 가까운 위협이 지배하므로,
정확한 상쇄가 일어나려면 **방향과 거리가 동시에** 대칭이어야 한다 (실질적으로 일어나지 않는다).

```
R = BOT.DANGER_RELEASE_RADIUS_PX          // 300. 새 상수를 만들지 않는다
for g in dangerPositions:
  d = botPos - g;  dLen = |d|
  if dLen < 1e-6: continue
  w = max(0, (R - dLen) / R)               // dLen=0 → 1, dLen>=R → 0
  sum += (d / dLen) * w
```

`R`로 `DANGER_RELEASE_RADIUS_PX`를 재사용하는 이유: 그 값이 이미 "봇이 위험으로 치는 바깥 경계"다.
가중치가 그 경계에서 **정확히 0**이 되므로, 고블린이 경계를 넘나들 때 합이 **계단식으로 튀지 않는다**
— 이것 자체가 진동원 하나를 더 제거한다. 새 밸런스 축을 만들지 않는다는 점도 중요하다
(`RULES.md` §7.0: 봇의 손잡이는 3개로 고정).

### B1b — §7.6 "서성이며 기다린다" 분기의 입력 필터

`bot.ts` 353행이 `computeFleeDir`에 **LOS가 뚫린 모든 고블린**을 넘긴다. B1의 가중치는 `R` 밖에서
0이므로, 맵 반대편 고블린이 섞이면 전부 0이 되어 무의미해진다.

→ 그 목록을 넘기기 전에 **거리 ≤ `BOT.DANGER_RELEASE_RADIUS_PX`** 로 거른다.
(이 분기의 진입 조건이 `nearestD <= BOT.RISK_TOLERANCE_PX`(220) < 300 이므로 **목록이 비지 않는다.**)

### B2 — 폴백 교체

```
if (|sum| < 1e-6):
   sum = lastFleeDir            // 직전에 실제로 쓴 도주 방향(길이>0). 없으면
   sum = -botFacing             // 기존 폴백 (라운드 첫 틱 등)
```

`lastFleeDir`은 `createBotPolicy()`가 봇마다 하나 갖는 지속 상태이고, `computeFleeDir`이
**정상 방향(비퇴화)을 낼 때마다** 갱신한다. 목적은 **연속성**이다 —
상쇄는 대개 순간적이므로, 그 한두 틱을 직전 방향으로 버티면 진동이 생기지 않는다.
**반전(`-facing`)은 원인이지 대책이 아니었다.**

### B3 — 계측만 한다 (이번엔 고치지 않는다)

`computeFleeDir`은 마지막에 `navDir(botPos, awayPoint, ...)`을 통과한다(§7.5의 의도: 벽 구석에
갇히지 않게). 그런데 `awayPoint`는 300px 앞이고 **격자 간격은 384px**이라, 격자 라우팅으로 새면
봇이 최대 384px 떨어진 12개 고정점 중 하나로 향한다 — 그 방향이 위협 쪽일 수 있다.

→ **코드를 바꾸지 말고 카운터만 넣는다.** FLEE 틱마다 `navDir`이 어느 갈래를 탔는지 집계:
`straight`(직선 LOS) / `entry`(격자 진입) / `next`(격자 전진) / `fallback`(`nextId === entry`).
`playtest`가 이 4개 비율을 보고한다. B1·B2 적용 후에도 `entry`+`next`가 지배적이면
**그때 B3를 별도 스펙으로 연다.** 지금 손대면 원인 분리가 안 된다 (한 번에 한 축).

## 3. 완료 기준 (기계 판정)

아래 임계값은 **이 1회성 수리의 인수 기준**이지 게임 밸런스 수치가 아니다.
런타임 코드가 읽지 않으므로 `balance.ts`에 넣지 않는다 (넣으면 밸런스 축이 하나 늘어난다).

**게이트 0 — 착수 여부 (0단계 결과로 판정)**

| 반전율 | 판정 |
|---|---|
| **≥ 10%** | 가설 확정. B1·B2 착수 |
| 5% ~ 10% | 회색. **착수하지 않는다** (씬이 더 비싸다). 결과만 WORKLOG에 남긴다 |
| **< 5%** | **가설 기각.** 이 스펙을 폐기하고 `bot.ts`를 건드리지 않는다. 원인은 다른 데 있다 |

**게이트 1 — 수정 인수 (B1·B2 적용 후, `balance.ts` 무변경, 동일 6시드 × 200회)**

1. FLEE 방향 반전율 **< 5%**
2. 실측 이격 속도 **≥ 6.0 px/s** (현재 2.2 → 2.7배 이상)
3. `stuckRuns` **≤ 10** (현재값 이하 — 회귀 금지)
4. `npm run sim`이 6시드 전부 크래시 없이 완주
5. `node scripts/check-boundary.mjs` 통과 (`bot.ts`에 Phaser 유입 없음)

1·2를 **둘 다** 만족해야 인수다. 하나만이면 원인 지목이 부분적으로 틀린 것이므로 보고한다.

> 왜 6.0인가: 이론 15 px/s에 벽 손실 90.8%를 곱하면 방향이 완벽해도 상한이 그리 높지 않고
> (고블린도 벽 손실을 겪으므로 정확한 상한은 미상), FLEE 대시가 평균 +8 px/s쯤 얹힌다 —
> **둘 다 손계산 추정이다.** 그래서 상한이 아니라 "현재의 2.7배"라는 **개선 배수**로 잡았다.
> 인수 후 실제 도달값은 `playtest`가 그대로 보고한다.

**클리어율은 이 수리의 인수 기준이 아니다.** 클리어율이 오르든 내리든 수리는 성공일 수 있다.
자를 고치는 일과 재는 일을 섞지 않는다.
