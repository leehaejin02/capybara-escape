## 3. 협업 · 분업 방식

### 3.1 사전 과제 — 사람 1인 + AI 에이전트 5종

팀원 대신 **역할이 분리된 AI 에이전트 5종**에게 일을 나눴다. 각 에이전트는
소유 파일과 사용 가능한 도구가 제한돼 있어, 사람 팀의 분업과 같은 방식으로
서로의 영역을 침범하지 못한다.

| 에이전트 | 담당 | 소유 파일 | 도구 제한 |
|---|---|---|---|
| `director` | 요구 접수 → 라우팅 | 없음 | 쓰기 불가(읽기·기록만) |
| `gd` | 무엇을 만들까 / 수치 | `docs/`, `src/config/balance.ts` | 코드 실행 불가 |
| `tech` | 어떻게 만들까 / 코드 | `src/` (balance.ts 제외) | 밸런스 수치 결정 불가 |
| `playtest` | 수치가 맞는가 | 없음 (읽기 전용) | 코드 수정 불가 |
| `verify` | 기준을 만족하는가 | 없음 (읽기 전용) | 코드 수정 불가 |

기본 흐름은 **director → gd → 사람 승인 → tech → playtest → verify**다.
단계를 건너뛸 수 있지만 **왜 건너뛰는지 반드시 남긴다.**

상세한 프롬프트·하네스 설계·실패 사례는 **제출물 4번 「AI 활용 기술 문서」**에 있다.

### 3.2 본선 — 3인 분업

| | 이해진 | 지승제 | 유한결 |
|---|---|---|---|
| **주** | 구현 · 에이전트 운영 | 기획 · 규칙 확정 | 아트 · 영상 |
| **부** | 배포 · 검증 | 문서 · 발표자료 | UI 배치 검토 |

- **의사결정**: 되돌리기 어려운 선택(스코프 변경, 의존성 추가, 배포)은 3인 합의.
  근거 없는 결정은 `docs/DECISIONS.md`에 남기지 않는다는 규칙을 그대로 가져간다.
- **충돌 처리**: 기획(지승제)과 구현(이해진)이 부딪히면 **스코프를 늘리는 쪽이
  무엇을 버릴지 함께 제시**한다. 순증가 제안은 채택하지 않는다.
- **기록**: 작업 단위마다 커밋한다. 누가 무엇을 했는지가 커밋 author로 남는다.
