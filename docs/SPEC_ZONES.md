# SPEC_ZONES — 맵 아트 개편: 벽 두께 · 소품 · 구역 3종 (전부 렌더 전용)

> 작성: `gd` / 2026-08-07 / 대상: `tech` 타일 생성 스크립트 + 렌더 씬, `verify` 기계 검사
> 상위: `docs/GDD.md` 8장 · 10장 → `docs/ART.md` §1(팔레트 원본) → **이 문서**
> 색의 원본은 **`ART.md` §1.1**이다. 이 문서는 그 색을 **어느 구조의 어느 면에 배정하는가**를 정한다.

## 이 문서를 만든 이유

사용자가 던전 탑다운 맵 레퍼런스를 제시하고 현재 맵이 **"형편없다"** 고 판정했다. 원인은 취향이 아니라 **구조 3개**다.

| # | 결함 | 이 문서의 대응 | 우선순위 |
|---|---|---|---|
| 1 | **벽에 두께가 없다.** 32×32 평면 벽돌이라 "바닥에 그린 무늬"로 읽힌다 | §3 벽 3단 구조(윗면/앞면/드롭섀도) + 이웃 마스크 4변형 | **1위** |
| 2 | **소품이 0개다.** 바닥과 벽뿐이라 비어 보인다 | §4 충돌 없는 장식 레이어 (구역별 4종) | **2위** |
| 3 | **16색으로는 위 둘이 불가능하다.** 벽 3단 × 3구역만 9색이다 | §2 팔레트 16 → **30색** 확장 | 1·2의 전제 |

> **시간이 부족하면 §3(벽)만 하고 멈춰라.** 단일 항목으로 체감 개선이 가장 크다.
> 그다음 §4(소품), 그다음 §5(구역 3종), 마지막 §6(은신 시각화). **반쯤 된 4개보다 완성된 2개가 낫다.**

## §1. 경계 — 이 스펙이 건드리지 않는 것

| 구분 | 이 스펙이 하는 것 | 하지 않는 것 |
|---|---|---|
| 맵 데이터 | 없음 | **`src/sim/map.ts` 한 글자도 고치지 않는다** |
| sim | 없음 | **sim은 구역·벽 두께·소품의 존재를 모른다.** 판정식 전부 그대로 |
| 밸런스 | 없음 | 구역별 속도·시야 차이를 만들지 않는다. **`playtest` 재측정 불필요** |
| 충돌 | 없음 | 소품은 **통과 가능**하다. `isSolid`는 여전히 `#`만 true |

GDD 10장 WON'T **"맵 2개 이상"을 위반하지 않는다.** 맵은 여전히 `MAP_ROWS` 하나이고,
구역·벽 변형·소품은 **같은 논리 타일을 다르게 그리는 것**뿐이다. 렌더 레이어에만 존재한다.

**렌더 깊이(depth) 순서 — 전 항목 공통.**

```
바닥 타일 < 벽 드롭섀도 < 소품 < marker_* < 캐릭터(카피바라·고블린) < 수풀 캐노피 < UI
```

수풀 캐노피만 캐릭터 위에 온다. 그게 §6(은신 시각화)의 전부다.

## §2. 팔레트 — 16색 → **30색**으로 확장한다

### §2.1 결정과 근거

**확장한다.** 16색은 우리가 스스로 건 제약이고 대회 요구가 아니다. 그리고 이번엔 취향 문제가 아니다 —
**벽 3단 구조가 색을 요구한다.** 한 구역의 벽 하나에 윗면·앞면 2색이 필요하고, 그 사이에 바닥이 끼며,
드롭섀도가 그 아래에 온다. 구역이 3개이므로 **벽 관련만 최소 9색**이다. 16색 안에서는 캐릭터 색을
깎아야 하고 그건 §2.4 판별성 조건(C1·C3)을 깬다.

**왜 30인가 — 역산이다. 감으로 고른 수가 아니다.**

| 묶음 | 수 | 내역 |
|---|---|---|
| 캐릭터·UI 공용 (기존) | 10 | `ink` + 카피바라 6 + 고블린 2 + `accent_amber` |
| 고블린 개선 (신규) | **2** | `goblin_shadow`(피부 명암 3단) + `goblin_cloth`(허리천). 레퍼런스 반영분 |
| 구역 무관 타일 (기존) | 3 | `tile_bush_dark` `tile_bush_mid` `tile_spa` |
| 벽 윗면 (신규) | **3** | 구역당 1색. **3단 구조의 핵심이고 대체 불가** |
| 동굴 세트 | 3 | `cave_wall_face`(구 `tile_wall`) + `cave_floor` + `cave_floor_shade` (뒤 둘은 hex 변경) |
| 마을 세트 (신규) | **3** | `earth_mid` `earth_dark` `warm_tan` |
| 숲 세트 (신규) | **3** | `forest_wall` `forest_floor` `forest_floor_shade` |
| 소품 전용 (신규) | **1** | `ember_red` (불꽃·버섯 갓·꽃) |
| S1/S4 화면 전용 (신규) | **2** | `sky_soft` `sky_pink` — **PNG에는 0픽셀** |
| 합계 | **30** | PNG 허용은 이 중 **28색** |

늘어난 14색 중 **11색이 §3(벽 3단)·§4(소품)의 직접 요구**다. 나머지 3색(고블린 2 + UI 2 중 …)은
사용자가 제시한 레퍼런스(고블린 허리천·로고 색감)의 반영분이다. **장식으로 늘린 색은 0개다.**

### §2.3 왜 "로고처럼 파스텔로 밝게"는 채택하지 않았나

**바닥은 밝게 만들 수 없다.** 상한이 계산으로 정해져 있다 — §2.4 C1이 **보행 가능 타일의 지배색은 L ≤ 117**을
요구한다(고블린 본색 L 177과 60 이상 벌려야 한다). L 117은 파스텔이 아니다.

대신 세 갈래로 나눠 처리했다.

1. **바닥은 명도가 아니라 색상(hue)을 로고 쪽으로 옮긴다.** 차가운 회보라(현행 `#5C5666`)를
   따뜻한 황토(`earth_mid` 111)·초록(`forest_floor` 102)으로 바꾼다. 명도는 상한까지만 올린다.
2. **밝음은 "고블린이 설 수 없는 면"에서 산다.** 벽 **윗면**은 캐릭터가 올라설 수 없으므로 C1을 면제받는다
   (§2.4 C1의 적용 범위). 그래서 `village_wall_top`을 **L 168**까지 밝게 잡았다 — 화면에서 가장 밝은
   대면적 색이 여기다. 3단 벽이 곧 "밝음의 예산"을 만들어 준 셈이다.
3. **로고 수준의 파스텔은 S1(타이틀)·S4(결과) 배경에서 쓴다** (`sky_soft` `sky_pink`).
   그 화면에는 캐릭터 판별 요구가 없어 공짜다.

**따라서 인게임은 사용자가 기대한 만큼 밝아지지 않는다.** 이건 미달이 아니라 **제약의 결과**이고,
깨면 고블린이 보이지 않아 게임이 성립하지 않는다(GDD 2장). 근거는 `docs/DECISIONS.md` D9.

## §3. 【1위】 벽 3단 구조 — `tile_wall` 128×96 (4 × 3)

레퍼런스의 벽은 전부 **윗면(밝음) + 앞면(어두움) + 바닥 드롭섀도**다. 그래서 서 있는 구조물로 보인다.
사용자가 보낸 워크플로 도식(`BASE → ROUGH → **LIGHT: GIVES THE STRUCTURE DEPTH** → POLISH`)의
세 번째 단계가 정확히 이것이고, **우리 맵에 빠져 있던 것도 정확히 이것이다.**

### §3.1 이웃 마스크 — 어느 변형을 쓸지 결정한다

```
variant = (isSolid(col, row-1) ? 2 : 0) + (isSolid(col, row+1) ? 1 : 0)
frameIndex = zone * 4 + variant
```

| variant | 북 / 남 | 그림 | 뜻 |
|---|---|---|---|
| 0 | 바닥 / 바닥 | 윗면 + **앞면** + 북쪽 모서리선 | 가로 1칸 두께 벽 (우리 맵의 대부분) |
| 1 | 바닥 / 벽 | **전면 윗면** + 북쪽 모서리선 | 벽 덩어리의 맨 윗줄 |
| 2 | 벽 / 바닥 | 윗면 + **앞면** | 벽 덩어리의 맨 아랫줄 |
| 3 | 벽 / 벽 | **전면 윗면** | 벽 덩어리 내부 |

**동/서 이웃은 보지 않는다.** 마스크를 4비트로 늘리면 변형이 16개가 되고 시트가 4배가 된다.
남북 2비트만으로 "두께"의 90%가 나온다 — 두께는 **아래 방향에서만** 보이기 때문이다. (안 만들 것: §7)

### §3.2 타일 내부 구성 (32×32)

| 영역 | y | 내용 |
|---|---|---|
| 북쪽 모서리선 | 0 | `ink` 1px 전 구간. **variant 0·1만** (북쪽이 바닥일 때) |
| **윗면** | 0(또는 1) .. 16 | `WALL_TOP` 채움 + 구역별 윗면 무늬 |
| 경계선 | 17 | `ink` 1px 전 구간. **variant 0·2만** |
| 앞면 상단 광 | 18 | 구역별 `FACE_LIGHT` 1px 전 구간. **variant 0·2만** |
| **앞면** | 19 .. 31 | `WALL_FACE` 채움 + 구역별 앞면 무늬. **variant 0·2만** |

variant 1·3은 `y 0..31` 전체가 윗면이고, 윗면 무늬가 **y=31까지 이어져** 위 타일과 연결된다.

**앞면 높이 = 14px (y 18..31).** 근거: 카피바라·고블린 스프라이트는 발바닥이 y=27, 높이 22px이므로
바로 위 타일과 겹치는 세로 범위가 대략 12~16px이다. **캐릭터가 겹치는 구간이 항상 앞면(어두움)이 되도록**
맞춘 값이고, 그게 C1-W가 성립하는 이유다. 이 값을 줄이면 캐릭터가 밝은 윗면과 겹친다.

### §3.3 구역별 벽 색·무늬

| | 숲 (z0) | 마을 (z1) | 동굴 (z2) |

### §3.4 드롭섀도 — `tile_shadow.png` 32×32, 1프레임 (전 구역 공통)

```
그리는 조건: 바닥 타일 (col,row) 에 대해 isSolid(col, row-1) == true
```

| y | 내용 |
|---|---|
| 0..3 | `ink` 전 구간 (불투명) |
| 4..5 | `ink` 체커보드 — `(x + y) % 2 == 0` 인 픽셀만 |
| 6..31 | 전 투명 (알파 0) |

- 알파는 0/255만 쓴다(`ART.md` §2.3). **반투명 대신 디더링**이 픽셀아트의 정답이고 팔레트 검사도 산다.
- 구역별로 색을 나누지 않는다. `ink`(20)는 세 구역 바닥(102/111/73) 전부와 C2c(≥30)를 만족한다.
- 깊이: **바닥 위, 소품 아래.** 소품이 그림자에 먹히면 안 된다.

### §4.1 배치 규칙 — 결정적이다 (시드·상태 없음)

```
propAt(col, row):
  if tileChar(col,row) != '.'                     -> 없음   # B·S·M·E·P·G 타일에는 놓지 않는다
  if 어떤 M/E/P/G 앵커와의 체비쇼프 거리 <= 2      -> 없음

  if (h % 100) >= PROP_DENSITY_PCT                -> 없음
  return { zone: zoneOfRow(row), index: (h >> 8) % 4 }
```

이 3개 상수는 **밸런스가 아니다** — sim이 읽지 않고 `playtest`가 튜닝하지 않는다.

## §5. 【3위】 구역 3종 — 같은 맵을 세로 3행으로 나눈다

### §5.1 배치

```
zoneOfRow(row) = row < 13 ? ZONE_FOREST(0) : (row < 25 ? ZONE_VILLAGE(1) : ZONE_CAVE(2))
```

| zone | 이름 | 맵 row | 성격 |
|---|---|---|---|
| 0 `FOREST` | **깊은 숲** | 0 ~ 12 | 다층 초록, 낙엽, 우듬지. **탈출구 `E`(46,3)가 여기 있다** |
| 1 `VILLAGE` | **고블린 마을(집터)** | 13 ~ 24 | 따뜻한 흙길, 나무 울타리, 노천 온천 |
| 2 `CAVE` | **고블린 동굴** | 25 ~ 36 | 어둡고 축축한 석굴. **플레이어 시작 `P`(5,30)가 여기 있다** |

구역 경계 벽 줄(row 12, row 24)은 **위쪽 구역**에 속한다.

> ### ⚠️ 발주 지시와 남북을 뒤집었다 — 그 이유
>
> 지시는 *행1(위)=동굴=시작 / 행3(아래)=숲=탈출*이었다. **맵 데이터가 그 반대다.**
> `src/sim/map.ts`가 이미 단언하는 값: `P` = **(5, 30)** 맨 아래, `E` = **(46, 3)** 맨 위.
> 맵은 고칠 수 없고(§1) 고칠 필요도 없다 — **테마만 뒤집으면 지시한 서사가 그대로 성립한다**:
> *"동굴 바닥에서 시작해 마을을 가로질러 숲으로 빠져나온다."* 게다가 **위로 갈수록 밝아지므로
> 탈출 방향과 밝아지는 방향이 일치**한다. 원안보다 강한 신호다. 의도는 지켰고 방위만 바뀌었다.

### §5.2 맵 데이터가 이 배치를 지지한다 (검산 결과)

| 항목 | 숲 (z0) | 마을 (z1) | 동굴 (z2) |
|---|---|---|---|
| 미션 `M` | (5,5) (30,5) | (5,18) (30,18) (43,18) | (18,30) (43,30) |
| 고블린 `G` | (42,7) | (6,19) | (42,31) |
| 수풀 `B` | (9~10, 2~3) | (27~28, 22~23) | (14~15, 34~35) |
| 온천 `S` | 없음 | **(9~10,17~18) · (37~38,22~23)** | 없음 |

- **고블린이 구역마다 정확히 1마리씩** 시작한다. 배치를 새로 짜지 않았는데 그렇다.
- **수풀이 구역마다 정확히 1패치씩** 있다 → 어느 구역에서도 숨을 곳이 있다. 은신 MUST 승격의 근거가 하나 더 생겼다.
- **온천 2패치가 모두 마을에 있다.** 시그니처 규칙(은신 + 시간 2배)이 **중간 통과 구역의 성격**이 된다.
  동굴에서 나온 플레이어가 마을에서 한 번 느긋해질 수 있고 그 대가로 시간을 태운다. **온천 위치를 옮기지 않는다.**

### §5.3 바닥 — `tile_floor.png` 128×96 (4 variant × 3 zone)

`frameIndex = zone*4 + (col*7 + row*13) % 4` — variant 규칙은 `ART.md` §3.4 그대로, **바꾸지 않는다.**
전 구역 공통: `FLOOR_BASE` 채움 + §3.4의 variant별 `FLOOR_SHADE` 얼룩 좌표 + 기존 스티플 노이즈.

| zone | `FLOOR_BASE` | `FLOOR_SHADE` | 추가 요소 |
|---|---|---|---|

### §5.4 수풀 — `tile_bush.png` 64×96 (2 layer × 3 zone)

`frameIndex = zone*2 + layer` (layer 0 = 바탕, layer 1 = 캐노피 → §6).

**Z-B1 (전 구역 공통 · 은신 신호)**: layer 0에서 `{tile_bush_dark, tile_bush_mid}` 합계 면적 **≥ 50%**,
그중 `tile_bush_mid` **≥ 10%**.

> 테마보다 이 규칙이 우선한다. 마을의 `B`를 순수한 나무통 색으로 칠하면 플레이어가
> **"여기 숨을 수 있다"를 학습하지 못한다.** 구역별로 다른 것은 초록을 감싸는 구조물뿐이다.

| zone | 구성 (layer 0) |
|---|---|
| 0 숲 | `ART.md` §3.4 수풀 + **쓰러진 통나무** `capy_brown_dark` 가로 막대 `y 23..27` **x 전 구간(랩)**, 윗줄 y=23은 `earth_dark` 하이라이트 |
| 1 마을 | §3.4 수풀 + **나무통/상자** `earth_dark` 사각 (9,9)-(22,22) 모서리 1px 제거, 테두리 `ink`, 안쪽 `warm_tan` 가로 1px 2줄 y ∈ {13,18} (x 11..20) |
| 2 동굴 | §3.4 수풀 + **이끼 낀 바위**: 잎 블롭 5개 중 2개(중심 (20,5) r=2 / (11,24) r=2)를 `cave_wall_face`로 교체 + `accent_amber` 버섯 갓 3px 가로선 (14,16)-(16,16) |

- 숲의 통나무를 **x 전 구간 랩**으로 그리는 이유: 수풀 패치는 2×2 타일이라 가로로 이어지면 64px짜리
  통나무 하나로 읽힌다. 타일 안에 가둔 통나무 4개는 격자로 보인다. (A12: x=0·x=31 열 색 구성 동일 ✅)
- 마을의 상자를 **중앙에 가둔** 이유는 반대다. 2×2에서 상자 4개면 **쌓아 둔 짐더미**로 읽힌다.

### §5.5 온천 — `tile_spa.png` 32×96 (1 × 3)

**`ART.md` §3.4 그대로.** 온천 `S`는 맵상 전부 마을에 있다(§5.2).
**행 0·2는 행 1과 픽셀 완전 동일**하게 굽는다 — 그림 2장을 낭비하는 대신
**렌더 코드에서 예외 분기를 없앤다.** 모든 타일이 `zone*COLS + variant` 한 식으로 인덱싱된다.

## §6. 【4위】 은신 시각화 — 수풀 캐노피 1장

**은신이 MUST로 승격됐다**(GDD 10장). 규칙은 이미 sim에 있으므로, 시각 신호만 붙인다.

`tile_bush`의 **layer 1(캐노피)**: 바탕과 같은 잎 블롭 중 **위쪽 절반(y 0..15)만** 그리고 나머지는 알파 0.
**깊이는 캐릭터보다 위**(§1 깊이 표) → 수풀에 들어가면 잎이 카피바라를 덮어 **"숨었다"가 화면에 보인다.**

- 새 스프라이트가 아니라 같은 시트의 열 하나다. 비용이 거의 없고 효과가 즉각적이다.
- **온천 은신에는 별도 오버레이를 만들지 않는다.** 온천은 타일 자체가 이미 시각적으로 명백하고,
  "시간이 2배로 준다"는 HUD 타이머가 이미 보여 준다. 여기에 아트를 더 쓰면 §3·§4를 밀어낸다.
- 캐노피는 `HIDING.ENABLED`와 무관하게 **항상 그린다.** 렌더가 게임 상태를 판정하지 않는다(하네스 3).
